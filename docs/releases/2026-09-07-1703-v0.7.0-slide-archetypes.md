# 0.7.0 — template-authored slide archetypes

**Contracts package:** `0.7.0`

**Template contract revision:** `3` (was `2`)

**Contracts status:** published and remotely verified

**Release status:** [`v0.7.0`](https://github.com/Wingspan-Technology/efficio-pptx-contracts/releases/tag/v0.7.0) published 2026-09-07 18:51 UTC

## Why this contract changed

One PowerPoint template often has to serve several distinct presentation shapes —
an investor pitch, a quarterly review, a training deck — that share most slides
but differ on a handful. Before this release the only way to express that was to
duplicate the template or to overload inclusion policy and selection groups,
which conflated "this slide fits this kind of deck" with "this slide should be
included in this particular request".

Revision 3 adds optional, template-authored archetype metadata so a client can
narrow its slide catalog to the requested presentation shape *before* AI slide
selection runs. The vocabulary belongs to each template: the contracts package
owns the metadata shape, validation, reference resolution, and the deterministic
applicability rule, and owns no archetype names.

## Completed behavior

### Deck registry — `efficio_slide_archetypes`

Optional presentation-level tag storing a JSON array of definition objects:

- `archetype_id` — required, at most 120 characters, matching
  `^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`, unique across the registry;
- `name` — required, non-blank, at most 120 characters; names may repeat;
- `description` — optional, and when present non-blank and at most 1000
  characters;
- no additional properties.

Missing, blank, and `[]` all mean the template declares no archetype
restrictions. Definition order is preserved but carries no selection meaning.
Parsed names and descriptions are trimmed; IDs stay exact.

### Slide assignment — `efficio_slide_archetype_ids`

Optional slide tag storing a non-empty JSON array of unique archetype IDs the
deck registry defines. A missing tag means the slide is generic and universally
applicable. Blank and `[]` are invalid. JSON Schema cannot check a reference
against another tag, so cross-tag reference validity is enforced by the
handwritten SDKs.

### Applicability

- A generic slide applies to every declared archetype, and stays applicable when
  the registry is absent, blank, or empty.
- An assigned slide applies when its array contains the requested ID.
- An assigned slide against an absent or empty registry is invalid: there are no
  definitions for it to reference.
- With a populated registry, the requested archetype must be one of the
  definitions.
- Unknown slide references, malformed requested IDs, and unsupported requested
  IDs fail explicitly rather than silently filtering a slide out.
- There is no implicit ID trimming, case conversion, or fallback matching.

### Independence

Neither tag declares an `ai` block, so neither appears in the generated
slide-selection instruction. Archetypes affect applicability only: inclusion
policy, choice/bundle group structure, slide role, placement, ordering, and the
slide-selection response schema are unchanged and independent. No contract-wide
archetype enum, hardcoded business names, or generated archetype list exists.

### Public SDK surface

TypeScript, from the existing `/editor` entrypoint:
`DECK_SLIDE_ARCHETYPES_TAG`, `SLIDE_ARCHETYPE_IDS_TAG`, `SlideArchetype`,
`SlideArchetypeContractError`, `parseSlideArchetypes`, `parseSlideArchetypeIds`,
`resolveSlideArchetypeAssignment`, and `isSlideApplicableToArchetype`.

Python, from `efficio_pptx_contracts`: `SLIDE_ARCHETYPES_TAG`,
`SLIDE_ARCHETYPE_IDS_TAG`, `SlideArchetype`, `SlideArchetypeContractError`,
`parse_slide_archetypes`, `parse_slide_archetype_ids`,
`resolve_slide_archetype_assignment`, and `is_slide_applicable_to_archetype`.

`validate_slide_tags` gained a backward-compatible keyword-only `deck_tags=None`.
Slides without an assignment validate exactly as before with no deck context. A
present assignment is parsed structurally first, then reports
`missing_slide_archetype_context` without deck tags,
`invalid_slide_archetype_assignment` for a blank value,
`invalid_slide_archetype_context` for an unusable registry, and
`unknown_slide_archetype_reference` for an undefined ID. Existing structural
codes (`invalid_json`, `invalid_json_type`, `schema_violation`) are unchanged and
suppress duplicate semantic errors. `validate_deck_tags` reports
`invalid_slide_archetypes` for a semantically invalid registry, such as duplicate
IDs.

The contracts package deliberately exposes no bulk catalogue-filtering API: it
does not own consumer slide-catalogue shapes or selection-group rewriting.

## Compatibility and migration

Both tags are optional and additive; every valid revision-2 template remains
valid. The authored migration `0002-to-0003.json` is revision-only — its
`operations` array is empty, so the planner sets the deck revision to `3` and
adds, removes, or normalizes no archetype tags.

- Revision 2 → 3 produces only the deck revision patch.
- Revisions 0 and 1 → 3 keep all existing role, content-mode, and text-capacity
  migration behavior and finish at revision 3.
- A template already at revision 3 produces no patches.
- Existing archetype metadata survives migration byte-for-byte.
- Legacy templates receive no empty deck or slide archetype tags. An empty or
  missing registry *is* the legacy, unrestricted behavior and is never
  backfilled.

The authored migration format now accepts an empty `operations` array for a
revision-only step. The field itself stays required: a missing, non-array,
malformed, or unknown-operation value is still rejected, and the migration format
version stays `1`.

The only deck-defaults change is `efficio_template_contract_revision` from `"2"`
to `"3"`. Slide defaults are unchanged.

## Consumer work

Archetype metadata is authored in the template and consumed by whichever client
owns the slide catalogue. Filtering happens once, before the AI-selection
request is built; nothing downstream of that re-checks compatibility.

**Template Editor.** Authors the deck registry and the per-slide assignment
through the public SDK, using the typed parsers and the generated tag-name
constants rather than raw tag strings. Run the revision-3 migration through the
public planner as usual, and do not synthesize archetype tags for existing
templates. Pass `deck_tags` to `validate_slide_tags` for any slide that carries
an assignment, so unknown references are caught at authoring time.

**Slide Generator.** Publishes and passes through the deck and slide archetype
metadata unchanged. It does not filter slides, does not resolve assignments, and
does not enforce archetype compatibility during generation. Archetypes must not
enter the generated slide-selection instructions, and must not influence
inclusion policy, selection groups, role, placement, or ordering.

**Pod1, or whichever client owns slide selection.** Validates the requested
stable archetype ID and filters incompatible slides with
`is_slide_applicable_to_archetype` (TypeScript: `isSlideApplicableToArchetype`)
*before* constructing the AI-selection request. The predicate raises rather than
silently dropping a slide when the registry, an assignment, or the requested ID
is invalid, so surface those failures instead of treating them as "not
applicable". A generic slide — one with no assignment — stays in the catalogue
for every archetype.

**Selection groups.** Structurally independent of archetypes; the contracts
package neither rewrites nor reinterprets them. When filtering removes a slide
that a choice or bundle group references, reconciling that group is the
catalogue-owning client's responsibility. The contracts package intentionally
ships only the per-slide predicate and no bulk catalogue-filtering API, because
it does not own consumer catalogue shapes or selection-group rewriting.

No changes were made to the Slide Generator, Pod1, the Template Editor, or any
other repository as part of this release.
