## Purpose and audience

This note explains two additive package capabilities: the replacement of
independent character limits with one shared estimated text-capacity model, and
semantic categorical fills backed by presentation-level classification schemes.
It is the implementation handoff for the Template Editor Add-In, Slide Generator,
and other consumers of `efficio-pptx-contracts`.

The Template Editor agent should use this document to understand:

- which tags and table fields now exist;
- how capacity is calculated and validated;
- how existing templates migrate to revision 2;
- which Editor behavior must change after adopting package `0.6.0`;
- how reusable classification schemes are authored and validated;
- how `categorical_fill` keeps semantic model output separate from trusted RGB
  styling;
- which context-aware SDK APIs Slide Generator and the Editor must consume.

This note does not replace the authored contracts. The source of truth is
[text-capacity-tags.contract.json](../../contracts/shared/text-capacity-tags.contract.json),
composed into the text and table component contracts by the generator.
The categorical-fill source of truth is the presentation-level
`efficio_classification_schemes` tag plus the authored component contracts under
[`contracts/components/categorical_fill`](../../contracts/components/categorical_fill/).

The package version and template contract revision are independent. Package
`0.6.0` distributes the code and schemas; template revision `2` identifies the
tag representation stored inside a PowerPoint template.

## Why the model changed

The previous model exposed an aggregate character maximum plus minimum,
maximum, and target characters per item. Those values were difficult to keep
coherent and did not directly represent the visual resource that matters in a
PowerPoint text area: available lines.

The new model keeps two concepts separate:

1. `items` are semantic units: a title, paragraph, bullet, or numbered entry.
2. Lines are estimated visual usage after wrapping and explicit line breaks.

This permits two short items, one longer wrapped item, or another valid mixture
to share the same available space without imposing an arbitrary character limit
on every individual item.

## Public contract

The generated content shape has not changed:

```json
{
  "items": ["First semantic item", "Second semantic item"]
}
```

Text components use prefixed PowerPoint tags. Table cells use the same field
names without the `efficio_` prefix inside `efficio_table_config`.

| Text component tag | Table cell field | Requirement | Meaning |
|---|---|---|---|
| `efficio_max_lines` | `max_lines` | Required for text; optional for render cells | Strict maximum estimated lines across all items. |
| `efficio_estimated_chars_per_line` | `estimated_chars_per_line` | Required for text; optional for render cells | Approximate characters that fit on one line. |
| `efficio_min_items` | `min_items` | Required for text; optional with default `1` for render cells | Strict minimum semantic item count. |
| `efficio_max_items` | `max_items` | Required for text; optional for render cells | Strict maximum semantic item count. |
| `efficio_target_items` | `target_items` | Optional | Preferred item count for generation guidance only. |

Text component tag values are positive ASCII integer strings. Nested table-cell
values are positive JSON integers. Capacity values are deliberately editable:
automatic sizing provides initial estimates, while manual sizing lets an author
override them.

Only `efficio_min_items` has a static text default (`1`). The Editor must derive
or collect `efficio_max_lines`, `efficio_estimated_chars_per_line`, and
`efficio_max_items` before a text component is contract-valid.

The following fields are retired and must not be written by current consumers:

```text
efficio_max_chars
efficio_target_chars
efficio_min_chars_per_item
efficio_max_chars_per_item
efficio_target_chars_per_item
efficio_max_chars_per_line
```

Their unprefixed table-cell equivalents are retired as well.

`efficio_sizing_mode` remains on text components. It still selects whether the
Editor owns the capacity through automatic estimation or manual author input;
it is not itself a capacity value.

## Estimated-line calculation

The contracts SDK uses the same deterministic calculation in Python and
TypeScript:

1. Normalize `CRLF` and bare `CR` to `LF`.
2. Split every semantic item on `LF`.
3. Count Unicode code points in each resulting segment.
4. Estimate segment usage as:

   ```text
   max(1, ceil(code_points / estimated_chars_per_line))
   ```

5. Sum every segment from every item.
6. The content fits when the sum is less than or equal to `max_lines`.

Each item therefore consumes at least one line. An empty segment created by an
explicit line break also consumes one line.

Example with `max_lines = 4` and `estimated_chars_per_line = 20`:

| Content | Estimated use | Result |
|---|---:|---|
| One 18-character item | 1 line | Valid |
| One 35-character item | 2 lines | Valid |
| Two 18-character items | 2 lines | Valid |
| `"First line\nSecond line"` | 2 lines | Valid |
| Three 30-character items | 6 lines | Invalid |

This is intentionally an estimate, not exact PowerPoint text measurement.
Font metrics, word boundaries, PowerPoint layout, and manual line positioning
can produce a different visual result. Exact visual inspection remains a
consumer concern.

## Validation rules

The shared rules are:

- `max_lines` and `estimated_chars_per_line` must be present together;
- `min_items` defaults to `1` where the table contract permits omission;
- `min_items` must not exceed `max_items`;
- `max_items` must not exceed `max_lines` when both are present, because every
  item consumes at least one estimated line;
- `target_items`, when present, must be between the minimum and maximum;
- `target_items` is guidance and never changes validation bounds;
- `plain` text uses exactly one item and does not accept `target_items`;
- item strings must be non-empty;
- estimated total line usage must not exceed `max_lines`.

For a multi-item table cell with line capacity but no explicit `max_items`, the
effective item maximum is `max_lines`.

### Text components

All four strict fields are required. The text validation schema enforces the
item count, while semantic validation enforces estimated line usage.

### Table components

Capacity remains optional per cell. It applies only to cells with
`render_action: "render"`. Preserved cells retain their authored content and do
not receive capacity semantic checks.

When line capacity is used on a render cell, `max_lines` and
`estimated_chars_per_line` must be supplied together. Item-only limits remain
valid when no line capacity is configured.

### Data-bound components

Data-bound submission schemas remain intentionally free of AI sizing rules.
The persisted text tag set still has to satisfy the component contract, but the
data-bound content validator does not reject renderer-compatible content based
on these capacity values.

## Generation and repair behavior

The provider-facing V2 response schema still uses the renderer-compatible
`items` array. It exposes hard item counts through JSON Schema and explains the
estimated line capacity in the schema description. It does not emit a
per-item `maxLength` derived from the retired character fields.
The generic `minLength: 1` rule remains only to reject empty item strings; it is
not a replacement character-capacity setting.

After structural validation, the contracts SDK performs deterministic estimated
line validation. Content over capacity produces the repair rule and reason:

```text
estimated_line_limit
```

For tables, the same rule identifies the affected cell coordinate. This keeps
text and table repair behavior based on one shared calculation.

## Categorical-fill contract

### Purpose

Categorical fill lets many slide shapes reuse one semantic case system without
duplicating colors or business instructions on each shape. A model or trusted
backend selects a stable `case_id`; Slide Generator resolves the authored color
privately and applies it to the tagged shape or supported native group.

The first release deliberately supports solid RGB fills only. It does not support
theme colors, gradients, patterns, transparency, outlines, direct model-selected
colors, rationales, confidence values, defaults, or fallback cases.

### Presentation-level scheme registry

Authors store an optional ordered JSON array in the presentation tag
`efficio_classification_schemes`:

```json
[
  {
    "scheme_id": "selection_state",
    "instruction": "Decide whether each option should be selected.",
    "palette_mode": "rgb",
    "cases": [
      {
        "case_id": "selected",
        "label": "Selected",
        "description": "The option should be highlighted.",
        "fill": { "value": "17365D" }
      },
      {
        "case_id": "unselected",
        "label": "Unselected",
        "description": "The option should remain inactive.",
        "fill": { "value": "BFBFBF" }
      }
    ]
  }
]
```

The contract requires:

- at most 50 schemes per presentation;
- lower-snake-case scheme and case IDs, each at most 120 characters;
- one non-blank instruction per scheme;
- 2–32 cases per scheme;
- one non-blank label and description per case;
- exactly six uppercase hexadecimal RGB digits without `#`;
- unique scheme IDs across the registry and unique case IDs within each scheme.

Case IDs represent business meaning, not visual styling. Use `selected` and
`unselected`, for example, rather than `blue` and `gray`. A designer may then
change the palette without changing generated content or downstream business
logic.

### Component tags

Every independently classified target is one normal component:

```json
{
  "efficio_content_mode": "ai_generated",
  "efficio_component_id": "option_germany",
  "efficio_component_type": "categorical_fill",
  "efficio_content_role": "Germany",
  "efficio_classification_scheme_id": "selection_state",
  "efficio_prompt_instruction": "Use evidence for Germany only."
}
```

`efficio_classification_scheme_id` is required and must resolve to an authored
scheme. `efficio_content_role` and `efficio_prompt_instruction` remain optional,
but authors should use them where the component ID alone is insufficient context.
Sharing one scheme does not force components to share a result: each component
returns its own case ID.

If several physical shapes always represent one logical target, the presentation
may tag one native PowerPoint group as the component. Shape support and recursive
group filling are generation-engine responsibilities, not tag-contract behavior.
Cross-component same-case groups are not part of this release.

### Public content and AI context

Generated and data-bound content has exactly one field:

```json
{ "case_id": "selected" }
```

The per-instance V2 schema replaces the generic static content contract with the
referenced scheme's exact ordered enum. Missing or extra fields and unknown case
IDs are invalid. Whole-component `null` behavior remains owned by the consuming
V2 envelope, not by this component schema.

`project_component_context(..., deck_tags=...)` exposes only:

- the optional component role and prompt instruction;
- scheme ID and instruction;
- ordered case IDs, labels, and descriptions.

It never exposes fills, raw PowerPoint tag names, shape paths, or renderer
metadata. The model chooses a semantic case; it never chooses a color.

### Trusted normalization and rendering metadata

The Python SDK resolves the authored scheme to this private mapping:

```json
{
  "scheme_id": "selection_state",
  "cases": {
    "selected": {
      "fill": { "kind": "rgb", "value": "17365D" }
    },
    "unselected": {
      "fill": { "kind": "rgb", "value": "BFBFBF" }
    }
  }
}
```

This mapping is trusted artifact/runtime metadata. It must not be returned to an
AI caller or accepted from generated content. V2 and data-bound builders derive
the same mapping, and `build_component_render_metadata()` lets an importer store
the identical renderer-owned copy without reproducing scheme parsing.

Normalization validates the case against this trusted map and leaves the public
content unchanged. There is no unknown-case fallback, closest-case matching, or
default fill.

### Python SDK surface

The stable categorical-fill API includes:

```python
parse_classification_schemes(raw_value)
resolve_categorical_fill_scheme(component_tags, deck_tags)
build_component_render_metadata(component_type, component_tags, deck_tags=...)
```

These existing generic functions now accept optional keyword-only `deck_tags`:

```python
project_component_context(component_type, tags, deck_tags=...)
build_validation_content_schema(component_type, tags, deck_tags=...)
build_v2_component_contract(component_type, tags, deck_tags=...)
build_data_bound_component_contract(component_type, tags, deck_tags=...)
```

Existing text, table, and chart calls remain valid without `deck_tags`.
Categorical-fill calls fail clearly when the context is missing or the scheme
reference is invalid. Persisted V2/data-bound coherence checks require the
schema enum to match the private case map exactly.

### TypeScript Editor SDK surface

The `/editor` entrypoint exports:

```ts
CLASSIFICATION_SCHEMES_TAG
CLASSIFICATION_SCHEME_ID_TAG
DECK_CLASSIFICATION_SCHEMES_TAG
parseClassificationSchemes(rawValue)
resolveCategoricalFillScheme(componentTags, deckTags)
ClassificationScheme
ClassificationCase
ClassificationFill
ClassificationPaletteMode
```

The generated component metadata also includes `categorical_fill`, its required
scheme-reference tag, and its defaults. The typed parser mirrors structural and
unique-ID rules so the Editor can author and resolve schemes without maintaining
its own contract vocabulary. Its `ClassificationFill` value is exactly the
authored `{ "value": "17365D" }` wire shape; `kind: "rgb"` is derived only in
private renderer metadata and must never be written back into the deck tag.

### Content modes

The existing content modes keep their established meaning:

| Mode | Behavior |
|---|---|
| `ai_generated` | Include semantic scheme context and ask for one `case_id`. |
| `data_bound` | Accept one trusted `case_id` through the strict renderer-safe schema. |
| `preserve` | Leave the authored target unchanged. |
| `remove` | Remove the target through the existing component-removal flow. |

Data-bound categorical fill remains strict about case membership because the
case is required to resolve a safe renderer operation; “limit-free” means no AI
text sizing or chart-generation limits, not accepting arbitrary case IDs.

### Template revision and compatibility

This component and deck tag are additive. Existing templates do not need either,
so the current template contract revision remains `2` and no new migration is
authored. A template starts using categorical fill only when it adds a scheme
registry and a component referencing that registry. Such a template must be
re-imported so Slide Generator snapshots its dynamic schema and private mapping.

Package `0.6.0` is therefore backward compatible for templates that do not use
the new component. Downstream consumers must still update their registered
component/rendering support before importing a template that does use it.

## Template migration to revision 2

The deck tag `efficio_template_contract_revision` now has current value `2`.
The migration catalog is sequential and append-only:

```text
unversioned template -> revision 0 -> revision 1 -> revision 2
```

A template behind by multiple revisions is migrated one adjacent step at a
time by `planTemplateContractMigration`. Consumers do not jump directly to the
latest representation and do not implement migration rules themselves.

The planner is pure: it accepts deck, slide, and shape tag snapshots and returns
explicit set/remove patches. The Editor remains responsible for applying those
patches to PowerPoint, verifying the writes, and saving the document.

Migration-derived capacity is a compatibility estimate. For an automatically
sized component, the Editor should recalculate from current shape geometry when
practical after applying the migration.

### Text migration

For revision-1 text components, the migration:

- derives `max_lines` from an existing `max_lines` value or legacy `max_items`;
- chooses `estimated_chars_per_line` from the current value, the legacy
  characters-per-line value, `ceil(max_chars / max_lines)`, or the legacy
  maximum characters per item, in that order;
- defaults `min_items` to `1`;
- fixes plain text at exactly one item;
- defaults a missing multi-item maximum to `max_lines`;
- retains a valid `target_items` value;
- removes every retired character field.

### Table migration

For `efficio_table_config`, the migration processes each cell independently:

- preserved cells remove retired capacity fields without becoming renderable;
- item-only render cells remain item-only;
- render cells with enough count and character information receive the new line
  capacity fields;
- plain render cells can infer one line when character capacity exists;
- a multi-item render cell with character capacity but no line or item count is
  rejected because there is no safe deterministic conversion;
- output JSON is serialized deterministically.

A revision-2 template that still contains a retired top-level text tag or a
retired nested table-cell field is rejected. The consumer must not silently
ignore it or mark the template current.

## Slide Generator categorical-fill implementation handoff

After pinning published contracts `0.6.0`, the importer must pass the complete
deck tag map through `project_component_context()`,
`build_validation_content_schema()`, `build_v2_component_contract()`, and
`build_data_bound_component_contract()`. It must not parse the scheme registry
or duplicate its validation rules.

At import time, `build_component_render_metadata()` supplies the trusted private
case-to-fill map for the component's renderer metadata. Public AI input and
expected response schemas contain semantic case IDs, labels, descriptions, and
instructions only. RGB values must not enter public artifacts, repair context,
API responses intended for a model, or generated content.

At generation time, validate and normalize `{ "case_id": "..." }` with the
SDK, resolve that ID through the stored private metadata, and apply the resulting
solid RGB fill to the tagged shape or supported native PowerPoint group. Unknown
cases, missing metadata, malformed fills, and stale scheme references fail
clearly; there is no default or fallback color. Repair instructions must list
the allowed semantic case IDs without disclosing RGB values.

Templates using categorical fill must be re-imported after the consumer update
so their dynamic schema and private renderer metadata are captured together.
Templates without categorical-fill components need no categorical-fill-specific
conversion, but they still follow this release's revision-2 text-capacity
migration where applicable. Slide Generator keeps generation-v2 artifact version
`6` because the stored artifact envelope is unchanged; it registers the
additional component within that existing version instead of using a version
bump as a feature flag.

## Release and adoption sequence

1. Commit and publish contracts package `0.6.0`.
2. Drain or expire stored V2 drafts that contain the retired
   `aggregate_character_limit` repair reason.
3. Update the Template Editor and Slide Generator to the published version.
4. Run each consumer's complete checks.
5. Re-import templates so generated artifacts use revision-2 capacity rules.

Existing content payloads do not require conversion because the `items` shape
is unchanged. Existing templates do require the versioned tag migration.
