## Why this contract changed

Named feature: [Named Data Topics](../features/data-topics/README.md).
Detailed consumer handoffs: [Slide Generator](../features/data-topics/slide-generator.md)
and [Template Editor](../features/data-topics/template-editor.md).

Template authors need a stable, shared vocabulary for the data a deck talks
about — revenue, headcount, churn — so that downstream tools can label slides
consistently. Before this release there was no structured place for that: slide
purpose and content descriptions are free-form AI guidance, and archetypes
describe presentation shapes, not data.

Revision 5 adds optional, template-authored, name-only data topics. The
contracts package owns the metadata shape, validation, and reference
resolution; each template owns its own topic vocabulary.

## Completed behavior

### Deck registry — `efficio_data_topics`

Optional presentation-level tag storing a JSON array of exact
`{topic_id, name}` objects:

- `topic_id` — required, at most 120 characters, matching
  `^topic_[a-z0-9]+(?:_[a-z0-9]+)*$`, unique across the registry;
- `name` — required, non-blank, at most 120 characters; names may repeat;
- no additional properties.

Missing, blank, and `[]` all mean the template declares no data topics.
Topics keep their authored order. Parsed names are trimmed; IDs stay exact.
Lengths are Unicode code-point counts in both SDKs.

### Slide assignment — `efficio_slide_data_topic_ids`

Optional slide tag storing a non-empty JSON array of unique topic IDs, with the
same ID bounds as the registry. A missing tag means the slide has no
assignment. Blank and `[]` are invalid. Resolution returns the referenced
definitions in the slide's authored order. JSON Schema cannot check a reference
against another tag, so cross-tag reference validity is enforced by the
handwritten SDKs.

Identifier checks match the full string in both SDKs, so trailing or embedded
line feeds are rejected even though JSON Schema `pattern` alone would accept a
trailing line feed in Python.

### Advisory only

Neither tag declares an `ai` block, so neither appears in the generated
slide-selection instruction or in deck AI context. Data topics do not bind data,
filter or select slides, or constrain generated content schemas. Inclusion
policy, selection groups, archetypes, role, placement, ordering, and every
component content contract are unchanged. No contract-wide topic enum or
hardcoded business vocabulary exists.

### Public SDK surface

TypeScript, from the existing `/editor` entrypoint: `DECK_DATA_TOPICS_TAG`,
`SLIDE_DATA_TOPIC_IDS_TAG`, `DataTopic`, `DataTopicContractError`,
`parseDataTopics`, `parseSlideDataTopicIds`, and
`resolveSlideDataTopicAssignment`.

Python, from `efficio_pptx_contracts`: `DATA_TOPICS_TAG`,
`SLIDE_DATA_TOPIC_IDS_TAG`, `DataTopic(topic_id, name)`,
`DataTopicContractError` (a `ValueError`), `parse_data_topics`,
`parse_slide_data_topic_ids`, and
`resolve_slide_data_topic_assignment(slide_tags, deck_tags)`.

`validate_deck_tags` reports `invalid_data_topics` for a registry that is
structurally valid JSON Schema but semantically invalid, such as duplicate topic
IDs or a newline-suffixed ID. `validate_slide_tags` reports
`invalid_slide_data_topic_assignment` for a blank or otherwise unparseable
assignment, and `unknown_data_topic_reference` when a reference cannot be
resolved: an ID the registry does not define, a call without `deck_tags`, or an
unusable deck registry. The issue message distinguishes those three cases.
Existing structural codes (`invalid_json`, `invalid_json_type`,
`schema_violation`) are unchanged and suppress the semantic data-topic codes, so
a malformed value is reported once. Slides without an assignment validate
exactly as before and need no deck context.

## Compatibility and migration

Both tags are optional and additive; every valid revision-4 template remains
valid. The authored migration `0004-to-0005.json` is revision-only — its
`operations` array is empty, so the planner sets the deck revision to `5` and
adds, removes, or normalizes no data-topic tags.

- Revision 4 → 5 produces only the deck revision patch.
- Revisions 0–3 keep all existing migration behavior and finish at revision 5.
- A template already at revision 5 produces no patches, and re-planning an
  applied plan produces no patches.
- Existing data-topic metadata survives migration unchanged.
- Legacy templates receive no empty deck or slide data-topic tags.

The only deck-defaults change is `efficio_template_contract_revision` from `"4"`
to `"5"`. Slide defaults are unchanged.

## Consumer work

**Template Editor.** Consume `0.10.0`. Author the deck registry and per-slide
assignments through the public SDK parsers and generated tag-name constants
rather than raw strings. Run the revision-5 migration through the public
planner, and do not synthesize data-topic tags for existing templates.

**Slide Generator.** Consume `0.10.0` and re-import templates as the revision
bump requires. Validate the raw registry and assignments during template import
with `validate_deck_tags` and `validate_slide_tags(..., deck_tags=...)`, and read
them through the typed parsers and resolver. Data topics must not bind data,
filter or select slides, constrain generated content schemas, or enter AI
instructions. The published catalog may carry topics as advisory data in its
existing AI input envelope; that does not change generated tag instructions.

**Other clients.** No change required. Slide-selection instructions, component
content contracts, and repair instructions are unchanged.

This package release contains Contracts changes only. Separate Slide Generator
integration and exact published-pin adoption are locally implemented and verified,
but are not merged or deployed by this release. Template Editor and DMS changes
are not included.
